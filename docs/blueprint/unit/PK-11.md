## Tujuan

Bulan atau tahun buku yang belum lewat tidak bisa ditutup, sehingga jurnal otomatis bertanggal hari ini tidak pernah
tertolak karena salah klik. Jurnal yang masuk selagi proses tutup berjalan menandai periode itu "Perlu tutup ulang".

## Perubahan

### Data

`period_closings`: nilai status baru `closing` (sedang ditutup) di samping `closed` dan `reopened`. `period_close_locks`:
field baru `token` (teks, id acak pemilik kunci). Tanpa migrasi.

### Server

`backend/services/closing_service.py`:

1. `def _today_wib() -> str` — `services.analytics_time.now_wib().date().isoformat()`. Dipanggil lewat nama modul supaya
   bisa diganti di tes.
2. `close_period`: sesudah `period_bounds`, **sebelum** mengambil kunci: bila `end >= _today_wib()` → `ValueError` dengan
   pesan di bawah (router sudah mengubahnya menjadi 400). Berlaku untuk `month` dan `year`.
3. `preview`: tambah `period_ended: bool` (= `end < _today_wib()`) dan `earliest_close_date: str` (sehari sesudah
   `end`); `can_close` = tidak ada penutupan tumpang tindih **dan** `period_ended`.
4. Kunci berpemilik: `_acquire_close_lock(...) -> str` mengembalikan `token` yang disimpan di dokumen kunci (juga saat
   mengambil alih kunci basi); pelepasan menjadi `delete_one({"_id": entity_id, "token": token})`.
5. Urutan `_close_period_locked`:
   1. Bereskan sisa proses terputus: tiap catatan PT ini berstatus `closing` — bila jurnal ber-`source_type` `closing`,
      `source_id` = id catatan, status bukan `void` ada → catatan dijadikan `closed` dengan `journal_entry_id` jurnal
      itu, `stale: true`, `stale_reason` "Proses tutup buku sebelumnya terputus — periksa lalu tutup ulang."; bila tidak
      ada → catatan dihapus.
   2. Periksa tumpang tindih dan gerbang suspense (tidak berubah).
   3. Sisipkan catatan berstatus `closing` (id, PT, jenis, kunci, label, tanggal awal-akhir, `closed_by`, `stale: false`).
   4. Hitung laba-rugi, bangun baris, sisipkan jurnal penutup ber-`source_id` id catatan.
   5. Perbarui catatan → `closed` beserta angka dan jurnalnya **tanpa menyentuh** `stale`, `stale_at`, `stale_reason`.
   6. Galat di langkah 4 → catatan `closing` dihapus, galat diteruskan.
6. `list_closings` tetap mengembalikan semua status.

`backend/services/gl_service.py`, `_mark_stale_closings`: saringan status menjadi `{"$in": ["closed", "closing"]}`.
`status_for_date` dan `_blocking_closing` tetap hanya membaca `closed` (catatan `closing` tidak mengunci posting).

`backend/services/entity_lifecycle_service.py:258` (`_open_periods`) menyaring status "bukan `reopened`"; ubah menjadi
`"status": "closed"` supaya catatan `closing` tidak terbaca sebagai penutupan terakhir.

## Di luar lingkup

- Satu fungsi tanggal buku WIB untuk semua jurnal dan kunci periode untuk dokumen → PK-37.
- Kontrol dua orang untuk buka periode dan buka kembali tutup buku → KF-T6. Daftar periksa tutup buku → PK-43.
- Indeks unik satu penutupan aktif per periode: tidak termasuk daftar PK-14; keunikan di sini dijaga kunci per PT.

## Asumsi dan risiko

- `ASUMSI:` "hari ini" = tanggal WIB server saat permintaan diterima; tidak ada masa tunggu tambahan sesudah akhir
  periode (sumber hanya meminta "akhir periode ≥ hari ini ditolak").
- `ASUMSI:` periode yang proses tutupnya terputus sesudah jurnal penutup terbit dianggap tertutup dan ditandai "Perlu
  tutup ulang"; tidak dibatalkan otomatis.
- `RISIKO:` pembaca lain `period_closings` belum mengenal status `closing`. Pembaca yang ditemukan:
  `backend/services/period_unlock_service.py:120` (`_closed_record`, sudah menyaring `closed`) dan
  `_open_periods` di atas. Cari ulang `period_closings` di `backend/` dan `scripts/` sebelum mengubah. Membatalkan:
  kembalikan commit dan hapus catatan `closing` bila ada.
