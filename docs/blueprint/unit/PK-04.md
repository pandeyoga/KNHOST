## Tujuan

Data keuangan yang bisa hilang bila server rusak turun dari paling banyak satu hari menjadi paling banyak enam jam.
Cadangan terakhir tiap bulan disimpan lebih lama dari cadangan harian. Ada satu perintah uji pulih yang membuktikan
sebuah arsip benar-benar bisa dipulihkan dan lolos penjaga data, tanpa menyentuh database yang sedang dipakai.

## Perubahan

### Data

Tidak ada koleksi atau field baru. Susunan folder cadangan:

| Tempat | Isi | Dihapus bila |
|---|---|---|
| `deploy/backups/<DB>-<YYYY-MM-DD_HHMM>.archive.gz` | Arsip database tiap kali jalan | Lebih tua dari `BACKUP_KEEP_DAYS` hari |
| `deploy/backups/uploads-<YYYY-MM-DD>.tar.gz` | Arsip unggahan, **sekali sehari** (dibuat hanya bila berkas tanggal itu belum ada) | Lebih tua dari `BACKUP_KEEP_DAYS` hari |
| `deploy/backups/bulanan/<DB>-<YYYY-MM>.archive.gz` | Salinan (tautan keras bila bisa) arsip database **terakhir** pada bulan itu; ditimpa tiap kali jalan di bulan yang sama | Bulannya lebih tua dari `BACKUP_KEEP_MONTHS` bulan dihitung dari bulan berjalan |
| `deploy/backups/.terakhir_ok` | Satu baris: waktu dan nama arsip cadangan terakhir yang lolos pemeriksaan | Ditimpa |

### Server

Hanya `deploy/backup.sh` dan satu baris di `deploy/install_vps.sh`. Tidak ada perubahan aplikasi.

**Perintah `deploy/backup.sh`**

| Perintah | Perilaku |
|---|---|
| tanpa argumen | Cadangkan sekarang: `mongodump` ke `<nama>.partial` → `gzip -t` → ganti nama ke nama akhir → perbarui salinan `bulanan/` → arsip unggahan bila belum ada untuk hari itu → salin `.env.last` → `prune` → tulis `.terakhir_ok`. Baris log akhir tetap `… backup OK → <berkas> (<ukuran>)` |
| `restore <arsip>` | Tidak berubah (menimpa database yang dipakai). Ditambah: menolak berkas yang gagal `gzip -t` |
| `verify [arsip]` | Uji pulih. Tanpa argumen memakai arsip database terbaru. Langkah: `gzip -t` → `mongorestore --archive --gzip --drop --nsFrom="$DB_NAME.*" --nsTo="${DB_NAME}_uji_pulih.*"` → jalankan penjaga data dengan `DB_NAME=${DB_NAME}_uji_pulih` dan `--only gl,gl_audit,numbering,tax,asset,budget,payment,variance,bank,case,contrabon,interco,closing` → cetak jumlah dokumen `journal_entries`, `cash_transactions`, `sales_orders`, `vendor_bills`, `users` di database sementara → hapus database sementara → baris akhir `uji pulih OK` atau `uji pulih GAGAL: <langkah>` |
| `prune` | Hanya membersihkan menurut retensi (dipakai juga oleh uji) |
| `install-cron` | Menulis `/etc/cron.d/kainnusantara-backup` dengan jadwal `BACKUP_CRON`; dijalankan sebagai root |

Aturan tambahan:

- Setiap kegagalan menghasilkan baris `<waktu> backup GAGAL: <langkah>` dan kode keluar bukan 0; berkas `.partial`
  dihapus. `.terakhir_ok` tidak diperbarui.
- `verify` menolak berjalan bila nama database sementara sama dengan `DB_NAME`, dan tidak pernah memakai `--drop`
  terhadap `DB_NAME`.
- Cara `verify` menjalankan penjaga data: bila kontainer backend memuat `/app/scripts/verify_data_integrity.py`
  (lingkungan A), pakai `exec` dengan `-e DB_NAME=…`. Bila tidak (fakta 7), jalankan kontainer sekali-pakai dari image
  yang sama dengan kontainer backend, di jaringan compose yang sama, dengan folder repo dipasang baca-saja di `/app`.
- Supaya bisa dicoba di lingkungan A, tiga hal yang kini ditulis mati boleh ditimpa lewat variabel lingkungan dengan
  bawaan = nilai sekarang: `KN_COMPOSE_FILE` (`deploy/docker-compose.yml`), `KN_ENV_FILE` (`deploy/.env`),
  `KN_BACKEND_CONTAINER` (`kn-backend`); juga `KN_BACKUP_DEST` (`deploy/backups`) dan `KN_CRON_FILE`
  (`/etc/cron.d/kainnusantara-backup`).
- `deploy/install_vps.sh`: baris cron yang ditulis mati diganti pemanggilan `backup.sh install-cron`.

## Uji penerimaan

`KN_COMPOSE_FILE=docker-compose.dev.yml KN_ENV_FILE=<berkas env uji> KN_BACKEND_CONTAINER=<kontainer backend dev>
KN_BACKUP_DEST=<folder sementara>`. Tiap baris menjadi satu fungsi di skrip uji baru `scripts/test_backup_sh.sh`.

## Langkah kerja

1. Tulis `scripts/test_backup_sh.sh` dengan U1–U12; jalankan: merah karena perintah `verify`, `prune`, `install-cron`
   belum ada.
2. Variabel yang bisa ditimpa (fakta 9) tanpa mengubah perilaku bawaan → U11.
3. Tulis-lalu-ganti-nama, `gzip -t`, baris GAGAL → U1, U2.
4. `prune`, folder `bulanan/`, unggahan sekali sehari → U6–U8, U10.
5. `verify` → U3–U5, U12. `install-cron` dan `deploy/install_vps.sh` → U9.
6. Dokumen operasi; gate `--quick`; laporan. Status unit menjadi `tahan` dengan catatan "menunggu U13 dari pemilik";
   temuan DB-03 baru ditulis `implemented_pending_review` sesudah U13 ditempel.

## Di luar lingkup

- Pulih ke titik waktu (`mongodump --oplog`) → PK-34, sesudah replica set.
- Menyalin arsip ke luar server (penyimpanan lain) → tidak ada di sumber; ditulis di laporan sebagai usulan untuk pemilik.
- Mengubah `deploy/docker-compose.yml` atau cara MongoDB dijalankan → PK-34.
- Memasukkan `scripts/` ke image produksi → tidak dikerjakan; `verify` memakai repo yang sudah ada di server.

## Asumsi dan risiko

- `ASUMSI:` jadwal bawaan empat kali sehari (02:30, 08:30, 14:30, 20:30 waktu server). Sumber hanya meminta "lebih
  dari sekali sehari"; angkanya bisa diubah lewat `BACKUP_CRON`.
- `ASUMSI:` arsip akhir bulan disimpan 12 bulan dan hanya arsip database; arsip unggahan mengikuti retensi harian.
- `ASUMSI:` arsip unggahan cukup sekali sehari, supaya pemakaian cakram tidak naik empat kali lipat.
- `ASUMSI:` uji pulih di server produksi boleh memakai database sementara pada MongoDB yang sama. Bila pemilik tidak
  menghendaki beban itu, U13 dijalankan di mesin lain dengan `KN_COMPOSE_FILE` lingkungan A dan arsip produksi.
- `RISIKO:` cakram penuh karena arsip database empat kali lebih banyak. Laporan memuat ukuran satu arsip × 56 (14 hari ×
  4) + 12 arsip bulanan dibanding sisa cakram; bila tidak muat, turunkan `BACKUP_KEEP_DAYS` sebelum `install-cron`.
- `RISIKO:` `verify` menulis ke MongoDB produksi (database sementara) dan menambah beban saat berjalan; dijalankan di
  luar jam sibuk. Database yang dipakai tidak disentuh (U3, U12).
- Titik henti: H2 (unit mulai `tahan`; pemilik melepasnya) dan H3 untuk U13. Membatalkan: kembalikan
  `deploy/backup.sh` dan `deploy/install_vps.sh` ke commit sebelumnya lalu jalankan `install-cron` versi lama (baris
  `30 2 * * *`); arsip yang sudah ada tetap bisa dipulihkan dengan `restore`.
