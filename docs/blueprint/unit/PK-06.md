## Tujuan

Jurnal antar-PT tidak lagi bisa terbit di satu PT saja tanpa jejak. Periode dan akun **kedua** PT diperiksa sebelum
dokumen berubah status; bila satu sisi tetap gagal, sisi itu bertanda gagal, tampil di panel Posting Gagal, dan bisa
diulang tanpa menggandakan sisi yang sudah terbit. Pelunasan antar-PT mencatat kas di kedua PT dan tidak bisa melunasi
dokumen yang sama dua kali.

### Server
**A. `gl_service.preflight_entry`** — kontrak sama dengan PK-05; dibuat unit yang lebih dulu dikerjakan:
`async def preflight_entry(*, lines, entity_id, date="", source_type="preflight") -> None` menjalankan pemeriksaan
`_insert_entry` (pemetaan akun, normalisasi, `_validate_entry_lines`, `enforce_closed_period_guard`) tanpa nomor dan
tanpa sisip; melempar `JournalValidationError` atau `ClosedPeriodError`.

**B. Berkas baru `backend/services/twin_journal.py`** — pembantu jurnal kembar (`02` §1 P6).

```python
@dataclass(frozen=True)
class TwinSide:
    key: str                        # "seller" | "buyer" | "payer" | "payee"
    entity_id: str
    lines: List[Dict[str, Any]]     # account_code, debit, credit, description
    description: str
    source_label: str
    status_doc: Tuple[str, str]     # (koleksi, id dokumen) tempat status sisi ini ditulis
    status_suffix: str = ""         # "" → gl_status/gl_error/gl_journal_id; "_payer" → gl_status_payer …

class TwinJournalError(ValueError): ...      # .side · .entity_id · .cause ("period" | "account")

async def preflight_twin(*, source_type: str, base_id: str, date: str, sides: Sequence[TwinSide]) -> None
async def post_twin(*, source_type: str, base_id: str, date: str, sides: Sequence[TwinSide],
                    created_by: str = "system") -> Dict[str, Dict[str, str]]   # {key: {status, journal_id, error}}
```

| Aturan | Isi |
|---|---|
| Kunci jurnal | `source_id = f"{base_id}:{side.key}"` — sama dengan yang dipakai hari ini, jadi jurnal lama dikenali |
| `preflight_twin` | Untuk tiap sisi yang jurnalnya **belum ada**: `preflight_entry` pada entitas sisi itu. Gagal → `TwinJournalError` yang menyebut PT-nya. Tidak menulis apa pun |
| `post_twin`, per sisi berurutan | Jurnal sisi itu sudah ada → tandai `posted`, lewati. Belum ada → `_insert_entry`; berhasil → `posted` + id jurnal; gagal → `failed` + `gl_error` (≤ 300 huruf) |
| Berhenti di kegagalan pertama | Sisi sesudah sisi yang gagal **tidak dicoba**; statusnya `failed` dengan `gl_error` "Belum dicoba karena sisi {key} gagal." |
| Tidak melempar | `post_twin` selalu mengembalikan hasil; pemanggil memutuskan jawaban |
| Ulang | Memanggil `post_twin` lagi dengan rencana yang sama hanya menerbitkan sisi yang kurang |

**C. Pemakai** (baris jurnal tiap sisi **tidak berubah** dari kode sekarang; hanya dipindah ke fungsi perakit rencana):

| Aksi | Urutan baru (`02` §1) |
|---|---|
| `interco_service.confirm` | PERIKSA: status `draft`, wewenang, `preflight_twin` (tanggal = saat ini) → NIAT: `atomic_claim.claim` pada dokumen penjual (prasyarat `status: "draft"`), lalu status pasangan `confirmed` + `gl_status: "pending"` → JURNAL: `post_twin` → SELESAI: lepas klaim, segarkan saldo dan eliminasi. Nilai 0 → `not_required` |

`interco_service.create_settlement(payload, actor, idempotency_key="")`:

1. PERIKSA — validasi yang ada; tiap transaksi tidak ber-`gl_status: "failed"`; untuk `transfer`/`cash`: rekening
   pembayar (`bank_account_id`, wajib milik PT pembayar dan aktif; kosong → rekening bawaan PT itu) dan rekening bawaan
   penerima harus ada; `preflight_twin` pada `settle_date`.
2. NIAT — sisip settlement `pending`; id = `ics_` + 24 heksa SHA-256 `<payer>|<kunci>` bila ada kunci. Id sudah ada dan
   `posted` → kembalikan dokumennya tanpa tulisan; `pending` → lanjut dari langkah yang belum bertanda.
3. EFEK 1 — per transaksi (termasuk baris `netted_against`) dan per dokumen pasangannya: `find_one_and_update` dengan syarat `status ∈ OPEN_STATUSES`,
   `settlement_ids` belum memuat id ini, dan `settled_amount + returned_amount + applied ≤ grand_total + 0,01`;
   `$inc settled_amount`, `$addToSet settlement_ids`; status `settled` bila tertutup. Gagal pada satu baris → baris yang
   sudah dinaikkan settlement ini dikembalikan (`$inc` negatif, `$pull settlement_ids`, status semula), settlement
   `cancelled`, 409.
4. EFEK 2 — `twin_cash` (`ref_type: "interco_settlement"`, `ref_id` = id settlement, tanggal `settle_date`); fungsi itu
   mendapat parameter opsional `out_account_id` dan `in_account_id`. Metode `netting` tidak membuat kas (tetap).
5. JURNAL — `post_twin` sisi `payer` dan `payee`. SELESAI — `posted`, saldo, eliminasi, tautan.

Fungsi ulang: `interco_service.repost_gl(pair_id, actor)`, `interco_service.repost_settlement_gl(settlement_id,
actor)`, `interco_return_service.repost_gl(return_pair_id, actor)` — merakit rencana dari dokumen (tanggal =

## Asumsi dan risiko

- `ASUMSI:` rekening penerima settlement = rekening bawaan PT penerima (`default_cash_account`), karena form sekarang
  hanya mengirim satu rekening; pilihan rekening penerima menyusul di PK-43.
- `ASUMSI:` bila sisi pertama gagal, sisi kedua tidak dicoba, supaya buku kedua PT tetap sama-sama kosong; rencana
  sumber hanya menuntut penjaga per sisi dan penanda gagal.
- `ASUMSI:` dokumen tetap `confirmed`/`approved`/`posted` walau ada sisi gagal (sesuai butir "Selesai bila" rencana
  sumber); pengamannya: transaksi berjurnal gagal tidak bisa dilunasi atau diretur sampai diulang.
- `ASUMSI:` akun kas pada jurnal settlement tetap seperti kode sekarang (`ACC_KAS_BESAR` di kedua sisi); kas kembar
  ber-`gl_posted: true` supaya tidak dijurnal dua kali.
