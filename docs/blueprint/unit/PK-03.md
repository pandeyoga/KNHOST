## Tujuan

Pemilik mendapat satu berkas `CEK_DATA.md` yang menjawab, per pemeriksaan, "sudahkah masalah ini terjadi di data
nyata, berapa banyak, dan apa tindak lanjutnya". Dari berkas itu diputuskan apakah perlu paket perbaikan data yang
terpisah dari perbaikan kode. Tidak ada data yang diubah dan tidak ada perilaku aplikasi yang berubah.

### Server

Tidak ada perubahan kode aplikasi. Berkas yang lahir, semuanya di folder baru `docs/reviews/2026-11-13/cek-data/`:

| Berkas | Isi |
|---|---|
| `docs/reviews/2026-11-13/cek-data/cek_data.js` (baru) | Skrip `mongosh` baca-saja. Memuat tiap kueri dari audit §12.2 dan dari dokumen kueri lanjutan bagian A dan B, satu fungsi per perintah kueri. Tiap fungsi dibungkus `try/catch` dan menghasilkan satu objek hasil. Di akhir skrip mencetak **satu** JSON |
| `docs/reviews/2026-11-13/cek-data/JALANKAN.md` (baru) | Petunjuk untuk pemegang data, lihat "Petunjuk" di bawah |
| `docs/reviews/2026-11-13/cek-data/keluaran-acuan.json` (baru) | Keluaran skrip di data acuan lingkungan A; bukti bahwa tiap kueri bisa berjalan |
| `docs/reviews/2026-11-13/cek-data/susun_cek_data.py` (baru) | Mengubah `keluaran.json` dan `penjaga.log` menjadi kerangka `CEK_DATA.md`; tidak membuka database |

**Bentuk satu objek hasil** (kunci tetap, dipakai `susun_cek_data.py`):

| Kunci | Tipe | Arti |
|---|---|---|
| `cek` | teks | ID pemeriksaan (aturan di bawah) |
| `temuan` | daftar teks | ID temuan audit yang diperiksa, mis. `["SL-01", "SL-04"]` |
| `ringkas` | teks | Kalimat komentar kueri di sumbernya |
| `status` | `ok` · `galat` | `galat` bila kueri melempar galat |
| `jumlah` | bilangan atau `null` | Banyak baris atau dokumen yang dikembalikan; `null` bila `galat` |
| `total` | bilangan atau `null` | Jumlah rupiah bila kuerinya menghitung nilai; selain itu `null` |
| `contoh` | daftar teks, paling banyak 5 | Nomor dokumen internal saja. Tanpa nama pelanggan, pemasok, karyawan, dan tanpa nominal per dokumen |
| `galat` | teks | Pesan galat; kosong bila `ok` |

**Aturan ID pemeriksaan**

| Sumber | ID | Contoh |
|---|---|---|
| Audit §12.2 nomor 1–17 | `Q-<nn>`; nomor yang berisi lebih dari satu perintah diberi huruf | `Q-05a`, `Q-05b`, `Q-05c`; `Q-07` |
| Kueri lanjutan bagian A dan B | `QL-<ID temuan pertama di komentar blok>`; lebih dari satu perintah diberi huruf | `QL-FY-01`, `QL-FX-05a` |
| Penjaga data | `INV-<kode invarian>` apa adanya dari keluaran penjaga | `INV-IC-01` |

Kueri yang hasilnya berupa daftar pembanding, bukan daftar pelanggaran (mis. `Q-01` daftar indeks, `Q-12` nilai roll dan
saldo akun per PT, `Q-13`), ditandai `jenis: "pembanding"` dan dinilai manusia; `jumlah` diisi banyak barisnya.

**Petunjuk di `JALANKAN.md`** (urutan tetap):

1. Pulihkan cadangan produksi ke **nama database lain** di MongoDB yang bukan produksi:
   `mongorestore --archive --gzip --nsFrom="<DB_NAME produksi>.*" --nsTo="kn_cek_data.*" < <berkas arsip>`.
2. Penjaga data, dari container backend lingkungan A:
   `docker compose -f docker-compose.dev.yml exec -e DB_NAME=kn_cek_data backend python /app/scripts/verify_data_integrity.py --only gl,gl_audit,numbering,tax,asset,budget,payment,variance,bank,case,contrabon,interco,closing --timing > penjaga.log 2>&1`.
3. Kueri: `mongosh --quiet kn_cek_data docs/reviews/2026-11-13/cek-data/cek_data.js > keluaran.json`.
4. Catat jumlah jurnal bukan `void` (`db.journal_entries.countDocuments({status: {$ne: "void"}})`); di atas 200.000
   hasil lapisan `gl` ditulis "terpotong" (fakta 5).
5. Serahkan `penjaga.log` dan `keluaran.json` ke `docs/reviews/2026-11-13/hasil/cek-data/`. Arsip cadangan dan
   database salinan **tidak** masuk repo; database salinan dihapus sesudah selesai.

### Berkas hasil `docs/reviews/2026-11-13/hasil/CEK_DATA.md`

Kepala: tanggal cadangan, nama berkas arsip, SHA kode saat skrip dijalankan, jumlah jurnal bukan `void`, siapa yang
menjalankan. Lalu satu tabel, satu baris per pemeriksaan:

| Kolom | Isi |
|---|---|
| Cek | ID pemeriksaan |
| Temuan | ID temuan audit |
| Yang dihitung | Kalimat `ringkas` |
| Jumlah | Angka; `galat` bila kueri gagal |
| Nilai (Rp) | `total`, berpemisah ribuan; `—` bila tidak ada |
| Contoh | Paling banyak 5 nomor dokumen |
| Usulan label | Diisi pelaksana menurut aturan di bawah |
| Label | Diisi atau dikukuhkan pemilik |
| Alasan / tindak lanjut | Wajib bila label bukan `bersih` |

**Label yang sah, ditulis persis:**

| Label | Dipakai bila |
|---|---|
| `bersih` | Jumlah = 0 dan status `ok` |
| `perbaiki data` | Jumlah > 0 dan buku jelas salah (mis. kas tanpa jurnal, jurnal antar-PT satu sisi, pembayaran tercatat dua kali) |
| `biarkan + alasan` | Jumlah > 0 tetapi sah atau tidak berakibat; alasannya ditulis (mis. dokumen uji, saldo awal yang memang dicatat manual) |
| `tanya pemilik` | Jumlah > 0 dan tindakannya butuh keputusan (mana sisi yang benar, dihapus-buku atau ditagih) |
| `tidak bisa dijalankan` | Status `galat`; kolom alasan memuat pesan galat. **Bukan** `bersih` |
| `dinilai manual` | Baris ber-`jenis: "pembanding"`; kolom alasan memuat hasil perbandingannya |

Pelaksana hanya mengisi "Usulan label". Bila ragu antara dua label, usulannya `tanya pemilik`.

Bagian penutup berkas, "Perlu paket perbaikan data?": tiga baris wajib dengan jumlahnya — jurnal antar-PT satu sisi
(`Q-09`, `INV-IC-01`), kas tanpa jurnal (`Q-07`), setoran karyawan ganda (`QL-FX-01`) — lalu semua baris berlabel
`perbaiki data`, dikelompokkan per unit blueprint pemegang temuannya, dan satu kalimat keputusan pemilik: ya atau tidak.

## Langkah kerja

**Bagian A — pelaksana, tidak menyentuh data nyata.**

1. Tulis `cek_data.js` dari kedua sumber; jalankan di data acuan sampai U1–U6 hijau.
2. Tulis `susun_cek_data.py` (U7) dan `JALANKAN.md`; simpan `keluaran-acuan.json`.
3. Tulis di `STATUS.md` bagian "Menunggu pemilik": "Mohon jalankan `JALANKAN.md` pada salinan cadangan produksi dan
   serahkan `penjaga.log` serta `keluaran.json`." Unit kembali `tahan`.

**Bagian B — pemilik atau pemegang data (titik henti H3).** Menjalankan `JALANKAN.md`.

**Bagian C — pelaksana, sesudah hasil diserahkan.**

4. Jalankan `susun_cek_data.py`; isi "Usulan label" dan alasan; tulis bagian penutup.
5. Pemilik mengukuhkan kolom "Label". Laporan `hasil/PK-03.md` menunjuk ke `CEK_DATA.md`.

## Di luar lingkup

- Memperbaiki data → paket perbaikan data tersendiri, diputuskan pemilik dari bagian penutup `CEK_DATA.md`.
- Empat pemeriksaan pada fakta 7 → dicatat di `CEK_DATA.md` sebagai "belum ada kueri"; temuan terkaitnya dipegang
  PK-28 (GR/IR), PK-30 (antar-PT), PK-19 (deposit), PK-15 (titipan bank).
- Sepuluh kasus uji laporan di dokumen kueri lanjutan bagian C → PK-41.
- Menjadikan kueri ini invarian tetap di `scripts/verify_data_integrity.py` → unit pemegang tiap temuan (`02` §5 D2).

## Asumsi dan risiko

- `ASUMSI:` bagian A boleh dikerjakan tanpa menunggu pemilik karena hanya menyentuh data acuan. Bila unit masih
  `tahan` saat gilirannya tiba, pelaksana menulis pertanyaan "Bolehkah bagian A dikerjakan sekarang?" (usulan: ya) dan
  melanjutkan unit lain.
- `ASUMSI:` nomor dokumen internal boleh masuk repo sebagai contoh; nama pihak dan nominal per dokumen tidak.
- `ASUMSI:` pemegang data punya MongoDB bukan-produksi untuk memulihkan salinan (mis. lingkungan A di komputernya).
- `RISIKO:` langkah pulih dijalankan terhadap produksi karena salah nama database. Penangkal: `JALANKAN.md` memakai
  `--nsTo="kn_cek_data.*"` dan tidak pernah memuat `--drop`; skrip `cek_data.js` berhenti di baris pertama bila nama
  database yang sedang dibuka sama dengan `DB_NAME` produksi yang ditulis pemegang data di kepala skrip.
- `RISIKO:` kueri lolos di data acuan tetapi galat di data nyata (field lama, bentuk berbeda). Barisnya menjadi
  `tidak bisa dijalankan`, kuerinya diperbaiki, dan hanya baris itu yang dijalankan ulang.
