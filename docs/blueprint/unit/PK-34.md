**T3 — berkas baru `backend/db_tx.py`.**

```python
TX_MODE: str                                   # env KN_TX_MODE: "off" | "auto" (bawaan) | "required"
async def transactions_available() -> bool     # perintah `hello` memuat `setName`; hasil disimpan
def current_session()                          # sesi transaksi tugas ini (contextvars) atau None
async def run_in_transaction(fn, *, label: str)  # fn: fungsi asinkron tanpa argumen
class TxUnavailable(RuntimeError)
```

| Aturan | Isi |
|---|---|
| Mode | `off`: `fn()` dijalankan langsung. `auto`: transaksi bila tersedia, selain itu langsung (dicatat sekali di log). `required`: aplikasi menolak mulai bila tidak tersedia — "KN_TX_MODE=required tetapi MongoDB bukan replica set. Periksa perintah mongod dan MONGO_URL." |
| Jalan | `async with client.start_session() as s:` → `await s.with_transaction(callback)`; `callback` menyetel `current_session` lalu `await fn()` |
| Bersarang | Bila sudah ada sesi aktif, `fn()` ikut transaksi itu (tidak membuka yang kedua) |
| Penerusan sesi | `db` di `backend/db.py` menjadi pembungkus tipis: tiap metode koleksi yang menerima `session` mendapat `session=current_session()` bila pemanggil tidak mengirimnya. Pemanggil lama tidak diubah |
| Serial | Operasi dalam satu sesi dijalankan bergantian (satu `asyncio.Lock` per sesi), karena sesi tidak boleh dipakai bersamaan |
| Log | Tiap transaksi mencatat `label`, lama (ms), jumlah ulang |

Larangan di dalam `fn` (diperiksa uji statik atas fungsi di tabel T4): memanggil layanan luar atau notifikasi;
`asyncio.create_task`; menulis master (`seed_default_coa` dipanggil **sebelum** blok); menulis penanda gagal — galat
dilempar keluar dan penanda (`gl_status="failed"`, `last_error` pada niat) ditulis pembungkus **di luar** transaksi.

**T4 — titik bungkus.** Polanya satu: PERIKSA dan NIAT di luar transaksi (niat harus bertahan bila transaksi batal);
`run_in_transaction` membungkus EFEK + JURNAL + SELESAI; galat → transaksi batal, niat tetap `pending` beserta galatnya.

| 2 | Jurnal kembar antar-PT | `twin_journal.post_twin` — kedua sisi dalam satu transaksi (PK-06) | `jurnal_kembar` |
| 3 | Settlement antar-PT | Langkah EFEK 1, `twin_cash`, `post_twin` di `interco_service.create_settlement` (PK-06) | `settlement_antar_pt` |
| 4 | Kwitansi piutang | Alokasi (`ar_allocation_service.allocate`), deposit, kas, jurnal di `create_receipt`; langkah-langkah `void_receipt` (PK-19) | `kwitansi`, `batal_kwitansi` |

## Asumsi dan risiko

- `ASUMSI:` anggota replica set dinamai `mongo:27017` (nama layanan compose) dan tidak ada klien di luar jaringan
  compose selain skrip host yang memakai `directConnection=true`.
- `ASUMSI:` otorisasi MongoDB tetap tidak dipakai (port tidak dipublikasikan di produksi), sehingga berkas kunci
  antar-anggota tidak diperlukan.
- `ASUMSI:` versi `mongomock-motor` di lingkungan B tetap bisa dipakai dengan menambal kelas klien baru; bila tidak,
  lingkungan B memakai klien tiruan milik `mongomock` langsung dan `03_LINGKUNGAN_UJI.md` dikoreksi.
- `RISIKO:` `callback` transaksi bisa diulang; efek di luar database di dalamnya akan terjadi dua kali. Dijaga U12.
- `RISIKO:` transaksi menunggu kunci hanya 5 milidetik dan berumur < 60 detik; pembayaran sangat besar atau dua
  pengguna pada dokumen yang sama memunculkan galat sementara. `with_transaction` mengulangnya; bila U11 > 5 detik,
  pecah per faktur dan laporkan.
- `RISIKO:` pembungkus `db` menyentuh semua akses data. Dijaga U4 (jumlah uji lulus sama) dan sakelar `off`.
- `RISIKO:` setelah menjadi replica set, `mongod` tidak boleh dijalankan lagi dengan perintah lama begitu saja. Jalan
  mundur produksi = pulih dari cadangan ke volume baru (panduan T5), bukan mengedit perintah.
