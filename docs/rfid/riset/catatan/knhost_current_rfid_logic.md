# KNHOST (Kain Nusantara ERP) — current RFID gate read logic and gap vs. unintended-read mitigation

Scope: code reading only at `main` HEAD `a8a3f6f` (2026-10-27). Nothing was executed against the backend; no hardware/middleware exists in the repo. All links are relative to the repo root (`../../` from this notes folder). "Inference" = derived by tracing code paths, not observed at runtime.

## 1. Ingestion — how reads reach the backend, what is accepted and stored

### Takeaway
Physical devices (via an external "Kotlin/Chainway" middleware that is NOT in the repo) push batches to `POST /api/rfid/ingest` authenticated by a per-device `X-Device-Key`. Per event the API accepts only `epc, event_id, captured_at, antenna (int), rssi (float)`; these go to a raw collection `rfid_observations`, but antenna/RSSI/captured_at are stored only — every decision uses server receive time and device-level config. No phase, Doppler, read count, trigger/sensor state, lane or direction field exists. No retention/TTL on any RFID log collection.

### Cited Findings
- Endpoint & auth: `POST /api/rfid/ingest` resolves the device from header `X-Device-Key`, then routes either to a verify session (`session_id`) or to `ingest()` — [backend/routers/rfid.py:589-597](../../backend/routers/rfid.py). Heartbeat `POST /api/rfid/heartbeat` (same auth) — [rfid.py:600-604](../../backend/routers/rfid.py).
- Payload schema: `IngestEvent{epc:str, event_id?:str, captured_at?:str, antenna?:int, rssi?:float}`; `IngestPayload{epcs:list[str], events:list[IngestEvent], batch_id?, session_id?}` — [rfid.py:559-571](../../backend/routers/rfid.py). Pydantic models do not declare phase/doppler/read_count/trigger/lane/direction, so such fields would be dropped (inference from model definition; `e.model_dump()` passed at [rfid.py:597](../../backend/routers/rfid.py)).
- Device auth: key hashed with SHA-256, stored as `api_key_hash` + 4-char hint, shown once on issue/rotation — [backend/services/rfid_ingest_service.py:22-40](../../backend/services/rfid_ingest_service.py); `authenticate()` 401 on missing/unknown key, 403 if `enabled is False` — [rfid_ingest_service.py:57-65](../../backend/services/rfid_ingest_service.py). Key issue endpoint admin-only — [rfid.py:578-586](../../backend/routers/rfid.py). Index on `rfid_devices.api_key_hash` — [backend/indexes.py:45-47](../../backend/indexes.py).
- Batch limit: `MAX_EVENTS = 500`; >500 → HTTP 413 `BATCH_TOO_LARGE`, nothing processed — [rfid_ingest_service.py:79](../../backend/services/rfid_ingest_service.py), [88-94](../../backend/services/rfid_ingest_service.py).
- EPC normalisation: separators stripped, uppercased, must be 24 hex (`try_canonical`); invalid EPCs are NOT rejected but kept as raw uppercase → later become red `UNKNOWN_EPC` — [backend/services/epc.py:14-16](../../backend/services/epc.py), [rfid_ingest_service.py:95-100](../../backend/services/rfid_ingest_service.py).

Antenna/RSSI/captured_at are NOT copied into `rfid_reads`.

- Side effect on tag: every known EPC read updates `rfid_tags.last_seen_at / last_seen_device_* / last_seen_location / last_seen_warehouse_id` — [rfid_ingest_service.py:202-206](../../backend/services/rfid_ingest_service.py).
- Response to middleware: per-EPC `{result, code, reason, action, roll_no, sku, product_name, read_id, duplicate?}` plus passage `{id, verdict, red_count, green_count, started_at, last_at}` and counters `accepted/duplicates/green/red` — [rfid_ingest_service.py:232-238](../../backend/services/rfid_ingest_service.py). Module docstring: RFID never changes stock; it answers green/red so middleware drives light/alarm — [rfid_ingest_service.py:1-8](../../backend/services/rfid_ingest_service.py).
- Indexes / retention: only `rfid_reads(device_id, epc, timestamp)` "dwell_lookup" and `rfid_passages(device_id, last_at)` are created — [backend/bootstrap.py:1662-1663](../../backend/bootstrap.py). No TTL (`expireAfterSeconds`) exists for `rfid_observations`, `rfid_reads`, `rfid_passages`, `rfid_incidents` (TTL is used only for sessions/idempotency/AI caches — [bootstrap.py:1589](../../backend/bootstrap.py), [backend/idempotency.py:101](../../backend/idempotency.py)).
- Export registry describes `rfid_passages` as "raw gate log (observation, not transaction)" and exposes `rfid_reads` — [backend/services/export_registry_more.py:198](../../backend/services/export_registry_more.py), [249](../../backend/services/export_registry_more.py).
- Legacy simulators: `POST /rfid/gate/simulate` now goes through the same `ingest()` path with `source="simulated"` (requires device `status == online`) — [backend/services/rfid_service.py:321-347](../../backend/services/rfid_service.py). `POST /rfid/reader/scan` simulates a fixed reader by writing an `info` read for up to 60 active tags of the warehouse via the older `_record_read` (bypasses observations/passages) — [rfid_service.py:350-368](../../backend/services/rfid_service.py), [299-318](../../backend/services/rfid_service.py).

### Inferences
- The data model can already carry antenna and RSSI per observation, so per-antenna sequencing or RSSI thresholds could be computed server-side from `rfid_observations` without a schema break — but only if middleware sends individual tag reports (not pre-aggregated), and the observation collection has no index on `(device_id, epc, captured_at)` to make such queries efficient.
- Because decisions use server receive time, store-and-forward batches sent after a network outage (promised in the middleware proposal) would be windowed and evaluated against the document state at upload time, not at capture time.

### Gaps
- The actual middleware (Kotlin) is not in the repo, so whether it already filters/dedups, sends `event_id`, per-antenna reports, or controls GPIO/lights cannot be verified (also stated in [docs/audit/wave-2/baseline/10_TEMUAN_RFID_GATE_DAN_INSIDEN.md:77](../../docs/audit/wave-2/baseline/10_TEMUAN_RFID_GATE_DAN_INSIDEN.md)).
- Deployed DB indexes/retention were not inspected (read-only constraint; no DB queries run).

## 2. Gate/session logic — passage, dedup, dwell, direction, arbitration, states

### Takeaway
There is a server-side "passage" concept, but it is a pure time-gap window (10 s since the last batch from the same device), not trigger-based. Dedup exists at three levels (event_id replay, same EPC within one passage, same EPC within 120 s on the same device) plus a 10-minute incident dedupe. There is NO trigger/photo-eye input, NO min-read-count, NO RSSI threshold/trend, NO antenna-sequence direction inference, NO cross-gate arbitration, NO static-tag learning/blacklist, NO stop/reverse/abort handling and NO candidate/confirmed/cancelled transaction state; the only states are per-read green/red/info, passage verdict + acknowledgement latch, and incident open/acknowledged/resolved. All thresholds are hard-coded constants.

### Cited Findings
- Constants: `PASSAGE_WINDOW_S = 10`, `DWELL_S = 120`, `MAX_EVENTS = 500` — [rfid_ingest_service.py:79-81](../../backend/services/rfid_ingest_service.py); incident `DEDUPE_MINUTES = 10`, `HEARTBEAT_STALE_SECONDS = 300` — [backend/services/rfid_incident_service.py:19-20](../../backend/services/rfid_incident_service.py); gate-status verdict TTL `ttl_s = 30` — [rfid_ingest_service.py:241](../../backend/services/rfid_ingest_service.py); kiosk `FETCH_STALE_S = 15`, `HEARTBEAT_STALE_S = 120`, polling 4 s — [frontend/src/features/rfid/GateLiveVerdict.jsx:11-12](../../frontend/src/features/rfid/GateLiveVerdict.jsx), [34](../../frontend/src/features/rfid/GateLiveVerdict.jsx).
- Passage = find the device's passage with `last_at >= now-10s`, else insert a new one (`rpsg_` id, device, warehouse, direction copied from device, epcs[], read_ids[], counters, verdict, acknowledged_at) — [rfid_ingest_service.py:103-115](../../backend/services/rfid_ingest_service.py). It is opened for every gate batch before EPCs are examined — [rfid_ingest_service.py:155](../../backend/services/rfid_ingest_service.py).
- Passage update on every gate batch: `$set last_at = now` unconditionally (even if all EPCs were duplicates), `$addToSet` EPCs/read ids, `$inc` red/green/info counts of NEW reads only; verdict = red if any red, else green if any green, else info ("red-dominant") — [rfid_ingest_service.py:220-229](../../backend/services/rfid_ingest_service.py).
- Dwell dedup: previous read of same device+EPC with `timestamp >= now-120s`; if it belongs to the SAME passage → only `observation_count++`, `last_observed_at`, returned as `duplicate: True`, no new read/incident; if a NEW passage → re-evaluated (fix G3 V3-RFID-01) — [rfid_ingest_service.py:156](../../backend/services/rfid_ingest_service.py), [160-178](../../backend/services/rfid_ingest_service.py). The dwell lookup compares against the read's creation `timestamp`, which is never refreshed (only `last_observed_at` is) — [rfid_ingest_service.py:162](../../backend/services/rfid_ingest_service.py), [172-173](../../backend/services/rfid_ingest_service.py).
- Per-EPC decision: unknown/inactive tag → red `UNKNOWN_EPC`; gate → `gate_evaluator.evaluate(direction, warehouse, roll)`; handheld/fixed reader → info `INVENTORY` — [rfid_ingest_service.py:179-188](../../backend/services/rfid_ingest_service.py).
- Gate evaluator (single evaluator for device, simulator, kiosk): decision based on the roll's ACTIVE MOVEMENT (putaway order, warehouse transfer, SO shipment), no green fallback — [backend/services/gate_evaluator.py:1-6](../../backend/services/gate_evaluator.py), movement resolution [48-83](../../backend/services/gate_evaluator.py).
  - IN: `in_transit_sales` → red `SALES_TRANSIT_NOT_INBOUND`; PA/transfer to another warehouse → red `WRONG_DESTINATION`; not active/not member → red `MOVEMENT_NOT_ACTIVE`; valid → green `MOVEMENT_IN`; transit w/o document → red `DOC_MISSING`; roll already belongs to this warehouse → info `LOCAL_ROLL`; else red `NO_DOCUMENT` — [gate_evaluator.py:91-104](../../backend/services/gate_evaluator.py).
  - OUT: quarantine → red; delivered/consumed → red `ALREADY_OUT`; `roll.gate_exit.movement_id == movement.id` → red `REPLAY_EXIT`; no movement → red `NO_DOCUMENT` (incl. `available` rolls); SO cancelled → red; source warehouse ≠ gate warehouse → red `WRONG_WAREHOUSE`; not in manifest → red `NOT_IN_MANIFEST`; movement not yet dispatched → red `NOT_RELEASED`; else green `MOVEMENT_OUT` — [gate_evaluator.py:106-126](../../backend/services/gate_evaluator.py).
  - Green OUT immediately stamps `inventory_rolls.gate_exit = {movement_id, device_id, at}` (after the read is durable) — [gate_evaluator.py:129-134](../../backend/services/gate_evaluator.py), [rfid_ingest_service.py:207-208](../../backend/services/rfid_ingest_service.py), [218-219](../../backend/services/rfid_ingest_service.py).
  - Guard-facing action text per code (e.g., "Tahan barang…") — [gate_evaluator.py:16-38](../../backend/services/gate_evaluator.py).
- Incidents: every red gate read calls `create_from_read`; atomic dedupe key `epc|device_id` while an open incident's `last_at` is within 10 min → `hits++` and `last_at` refreshed; new incident → notification `rfid_gate_alarm` (critical) to role warehouse; severity high if roll known else medium — [rfid_incident_service.py:35-96](../../backend/services/rfid_incident_service.py). States open → acknowledged → resolved (CAS) — [rfid_incident_service.py:110-139](../../backend/services/rfid_incident_service.py).
- Passage latch/ack: gate status returns the latest passage or the latest red un-acknowledged ("latched") passage, with reads, `age_s`, `expired` (age > TTL and not latched), heartbeat age — [rfid_ingest_service.py:241-263](../../backend/services/rfid_ingest_service.py). Acknowledge requires note ≥5 chars, sets `acknowledged_at/by/note` without touching reads/incidents — [rfid.py:417-427](../../backend/routers/rfid.py), [rfid_ingest_service.py:285-293](../../backend/services/rfid_ingest_service.py).

### Inferences (scenario walk-throughs, traced from code; not runtime-tested)
- **Static tag on a rack near the OUT gate** (roll `available`, no movement): first read → red `NO_DOCUMENT` read + incident + latched red passage. If the reader keeps reporting it at <10 s intervals, every batch bumps `passage.last_at`, so the passage never closes and all subsequent real loads are merged into this red-dominant passage. Because dwell compares to the read's creation time, a NEW red read is produced roughly every 120 s (incident `hits` keep incrementing since `last_at` is refreshed within 10 min). After the operator acknowledges, the same open passage stays `verdict=red`, not expired, so the kiosk keeps showing red (state = passage verdict) — i.e. one stray static tag can hold the OUT gate permanently red. Lines: [rfid_ingest_service.py:156-178](../../backend/services/rfid_ingest_service.py), [220-229](../../backend/services/rfid_ingest_service.py), [GateLiveVerdict.jsx:49-50](../../frontend/src/features/rfid/GateLiveVerdict.jsx).
- **Static tag near the IN gate** (roll local to that warehouse): info `LOCAL_ROLL` — no alarm, but it still keeps the IN passage open and pollutes the passage roll list and `rfid_tags.last_seen_*` (location view shows the roll "at the gate") — [gate_evaluator.py:102-103](../../backend/services/gate_evaluator.py), [rfid_ingest_service.py:202-206](../../backend/services/rfid_ingest_service.py), [rfid_service.py:372-401](../../backend/services/rfid_service.py).
- **Parked/staged load near the OUT gate before ERP dispatch** (rolls reserved/committed for an SO, shipment not dispatched): red `NOT_RELEASED` per roll → incidents/latched alarm while just waiting — [gate_evaluator.py:124-125](../../backend/services/gate_evaluator.py).
- **Parked load near OUT gate after ERP dispatch, then real exit later**: the parked reads are green `MOVEMENT_OUT` and immediately stamp `gate_exit`; when the truck actually passes in a later passage (>10 s gap), the evaluator returns red `REPLAY_EXIT` ("roll already exited") — a false alarm on the legitimate exit. Same for **approach-then-back-off then re-approach** at the OUT gate. No candidate state or "confirmed exit" step exists to prevent the premature stamp — [gate_evaluator.py:111-113](../../backend/services/gate_evaluator.py), [129-134](../../backend/services/gate_evaluator.py), [rfid_ingest_service.py:170-171](../../backend/services/rfid_ingest_service.py).
- **Cross-read between IN and OUT gates**: each device evaluates independently with its own direction. An outgoing roll (`in_transit_sales`) picked up by the IN gate's antennas → red `SALES_TRANSIT_NOT_INBOUND` at the IN gate (incident + latch), while the OUT gate shows green. An arriving PA roll read by the OUT gate → `NO_DOCUMENT`/`WRONG_WAREHOUSE`-type red. No arbitration (e.g., RSSI comparison or "claimed by other gate within X s") exists — [rfid_ingest_service.py:130-132](../../backend/services/rfid_ingest_service.py), [gate_evaluator.py:91-126](../../backend/services/gate_evaluator.py).
- **Repeated reads**: handled reasonably within one passage (duplicate flag), across retries (event_id), and for incidents (10-min hits). Not handled for continuously present tags beyond 120 s (new read each ~120 s, see above).
- **Concurrency**: `_passage_for` is find-then-insert without a unique guard; two simultaneous batches from one device could open two passages (minor; [rfid_ingest_service.py:103-115](../../backend/services/rfid_ingest_service.py)).
- Since IN/OUT is a device attribute, a physical gate with 3 antennas per side would be modelled as one device per side; the 3 antenna IDs would arrive only as `antenna` integers in observations, with no meaning attached.

### Gaps
- Real RF behaviour (stray-read rates, cross-lane reads at the actual site) is untested in all audits ([docs/audit/wave-2/baseline/10_TEMUAN_RFID_GATE_DAN_INSIDEN.md:77](../../docs/audit/wave-2/baseline/10_TEMUAN_RFID_GATE_DAN_INSIDEN.md); [docs/audit/gelombang-3/LAPORAN_LENGKAP.md:36](../../docs/audit/gelombang-3/LAPORAN_LENGKAP.md)).
- Whether the middleware drives lights/buzzer from the ingest response, or how it un-latches after acknowledgement, is unknown (no device-key endpoint exposes latch state).

## 3. From gate reads to business transactions; reconciliation vs expected lists

### Takeaway
Gate reads never create business transactions: they do not move stock, confirm putaway, dispatch or receive anything. The only write to business data is `inventory_rolls.gate_exit` on green OUT (used solely for REPLAY_EXIT) plus tag `last_seen_*`. Reconciliation against an expected list exists, but in separate handheld/manual "verify sessions" (print verify, loading check vs SO, RFID cycle count) and in putaway arrival (EPC list pasted in the UI) — not fed from gate passages. At the gate, membership is checked per EPC (NOT_IN_MANIFEST), but missing rolls of a manifest are not detected.

### Cited Findings
- Principle "RFID does not change stock" — [backend/services/rfid_service.py:1-11](../../backend/services/rfid_service.py), [rfid_ingest_service.py:4-7](../../backend/services/rfid_ingest_service.py). `gate_exit` has no consumer outside `gate_evaluator.py` (repo grep of `backend/` for `gate_exit`).
- Outbound: dispatch is done in ERP and guarded by the Final Loading Check (handheld sweep session `kind=loading_check` vs rolls reserved for the SO): blocks dispatch if a session is open, result not clean (missing/extra/untagged), simulated-only evidence, or manifest changed since check; warehouse policy `loading_check_policy` (`optional` default / `required`) — [backend/services/loading_check_service.py:42-49](../../backend/services/loading_check_service.py), [52-96](../../backend/services/loading_check_service.py), [99-128](../../backend/services/loading_check_service.py), [163-165](../../backend/services/loading_check_service.py), [278-326](../../backend/services/loading_check_service.py). Routes `/outbound/so/{id}/loading-check/start`, `/outbound/loading-check/{sid}/scan`, `/scan-label` — [backend/routers/outbound_picking.py:541-572](../../backend/routers/outbound_picking.py).
- Gate OUT is evaluated AFTER ERP dispatch: green only if shipment status ∈ {dispatched, in_transit, partially_shipped} and roll status `in_transit_sales` (SO) or transfer `dispatched` + roll `in_transit_transfer` or PA `in_transit` — [gate_evaluator.py:11](../../backend/services/gate_evaluator.py), [55-82](../../backend/services/gate_evaluator.py).
- Verify-session engine: `scanned_epcs` via `$addToSet`; `missing = expected − scanned`, `extra = scanned − expected`; `scan_log` keeps source/actor/device/count/first 50 EPCs (last 200 entries); simulated scans yield result `simulated` — [backend/services/rfid_print_service.py:280-308](../../backend/services/rfid_print_service.py), [320-339](../../backend/services/rfid_print_service.py).
- Device sweeps can be posted into a verify session only by `handheld`/`fixed_reader` (gate devices are rejected) — [rfid_ingest_service.py:296-307](../../backend/services/rfid_ingest_service.py).
- Putaway (transit → storage warehouse): PA dispatch moves rolls to `in_transit_transfer` after re-checking tag identity — [backend/services/putaway_order_service.py:272-307](../../backend/services/putaway_order_service.py). Arrival `confirm_arrival(scanned_epcs | manual_all+reason≥10)`: items whose EPC is in the scanned list land (stock moved, paired movements, BTG number), others → `exception` + journey `gate_exception`; exceptions resolved by `accept` / `return_transit` — [putaway_order_service.py:369-429](../../backend/services/putaway_order_service.py), [432-480](../../backend/services/putaway_order_service.py), router [backend/routers/putaway_orders.py:21-24](../../backend/routers/putaway_orders.py), [97-106](../../backend/routers/putaway_orders.py).
- The arrival EPC list comes from a textarea ("tempel EPC hasil baca") or a "Simulasi Scan Semua" button that submits all PA item EPCs — [frontend/src/features/wms/PutawayOrdersPanel.jsx:87-97](../../frontend/src/features/wms/PutawayOrdersPanel.jsx), [206-221](../../frontend/src/features/wms/PutawayOrdersPanel.jsx). No code links an IN-gate passage to `confirm_arrival`.
- `verify-labels` is QR-label based (no RFID): rolls in receiving stages scanned by roll number → journey `label_verified` — [putaway_order_service.py:483-505](../../backend/services/putaway_order_service.py), [putaway_orders.py:43-50](../../backend/routers/putaway_orders.py).
- RFID cycle count: expected = active tags of physical rolls in the warehouse; report only (found/missing/extra), no stock change — [backend/services/cycle_count_service.py:1-57](../../backend/services/cycle_count_service.py).
- Unexpected EPCs at the gate: unknown/inactive → red `UNKNOWN_EPC` incident (owner `None`, severity medium) — [rfid_ingest_service.py:181-183](../../backend/services/rfid_ingest_service.py), [rfid_incident_service.py:71](../../backend/services/rfid_incident_service.py); known roll not in manifest → red `NOT_IN_MANIFEST` — [gate_evaluator.py:122-123](../../backend/services/gate_evaluator.py).
- Original design planned a manifest-bound gate session `rfid_gate_sessions {gate_id, direction, source_type so_dispatch|gr|transfer, source_id, manifest_epcs[], reads[], alarms[], status}` — [memory/WMS_RFID_ANALYSIS.md:172](../../memory/WMS_RFID_ANALYSIS.md); no code references `rfid_gate_sessions` (repo grep).

### Inferences
- Because gate decisions are advisory (alarm only) and do not post transactions, unintended reads currently cause alarm noise, false incidents and polluted last-seen/location data, but not wrong stock — the risk is operational (alarm fatigue, guards learning to ignore red) rather than ledger corruption. The one exception is `gate_exit` stamping, which corrupts subsequent gate verdicts (REPLAY_EXIT).
- The existing verify-session engine (expected/scanned/missing/extra, scan_log, atomic close, simulated flag) is a natural building block for a manifest-bound gate passage, but it is currently not reachable from gate devices.

### Gaps
- Whether operations intend the IN gate to auto-confirm PA arrival (vs. paste EPCs) is not documented in code; only the UI copy says "Validasi gate-in" ([PutawayOrdersPanel.jsx:208](../../frontend/src/features/wms/PutawayOrdersPanel.jsx)).

## 4. Device configuration in the ERP (per device / antenna, UI)

### Takeaway
Configuration is per device only: `code, name, type (gate|fixed_reader|handheld|printer), direction (in|out, gates only), warehouse_id, location (zone/bin), status, enabled, API key`. ## 6. Gap analysis vs. mitigation techniques

### Takeaway
Of the ten techniques, the system has raw-log persistence and expected-manifest checking partially, dedup partially, and a rudimentary alarm/ack state; trigger windows, static-tag learning, RSSI trend/peak, antenna-sequence direction, cross-gate arbitration and configurable thresholds are missing. The most damaging current behaviours for the user's concerns are (a) time-gap passage that a static tag can hold open indefinitely, (b) immediate `gate_exit` stamp that turns a later real exit into REPLAY_EXIT, (c) per-device independent evaluation that converts IN/OUT cross-reads into red alarms.

### Inferences (concrete change hooks a writer could propose; derived from the code above)
- Ingest contract: extend `IngestEvent` with optional `read_count, phase, doppler, trigger/gpio state, lane_id, sequence/reader_boot_id`, and accept a separate trigger/GPIO event type so the backend (or middleware) can open/close passages on photo-eye edges instead of the 10 s gap ([rfid.py:559-571](../../backend/routers/rfid.py), [rfid_ingest_service.py:103-115](../../backend/services/rfid_ingest_service.py)).
- Passage: close after max duration and do not bump `last_at` on duplicate-only batches; base windows on `captured_at` when present ([rfid_ingest_service.py:220-226](../../backend/services/rfid_ingest_service.py)).
- Static tags: a per-device background list (EPCs seen continuously for > N min with stable RSSI and no trigger) excluded before evaluation, shown for supervisor review; stop updating `last_seen_*` from gate reads of background tags ([rfid_ingest_service.py:179-206](../../backend/services/rfid_ingest_service.py)).
- Direction/arbitration: per-device antenna map (e.g., antenna 1 = outer, 3 = inner) and gate pairing so an EPC seen by both IN and OUT within a window is attributed by RSSI peak/antenna order; until confident, mark passage `uncertain` (yellow) instead of red.
- Exit stamp: move `stamp_exit` from read time to passage close/confirmation (or only when the inferred direction is OUT with confidence), otherwise parked/back-off loads cause REPLAY_EXIT ([gate_evaluator.py:129-134](../../backend/services/gate_evaluator.py), [rfid_ingest_service.py:218-219](../../backend/services/rfid_ingest_service.py)).
- Manifest: bind a passage to an expected list (the planned `rfid_gate_sessions`, [memory/WMS_RFID_ANALYSIS.md:172](../../memory/WMS_RFID_ANALYSIS.md)) reusing the verify-session engine ([rfid_print_service.py:280-339](../../backend/services/rfid_print_service.py)) so missing rolls and extras are computed per passage; let IN-gate passages feed `confirm_arrival` instead of pasted EPCs ([putaway_order_service.py:372-429](../../backend/services/putaway_order_service.py)).
- Settings: register gate thresholds in the config catalog (scoped per warehouse/device) and read them via `config_resolver.value_of` as already done for `wms.rfid_simulation` ([loading_check_service.py:182-189](../../backend/services/loading_check_service.py)).
- Observability: add index on `rfid_observations(device_id, received_at)` / `(device_id, epc, captured_at)`, a TTL/retention policy, and a replay endpoint/script that re-runs passage logic over stored observations to tune thresholds offline.
- Middleware latch: expose a device-key-authenticated passage/latch status (current `/rfid/gate/{id}/status` needs a user session, [rfid.py:400-404](../../backend/routers/rfid.py)) so physical lights can follow acknowledgements.

### Gaps
- No empirical data (raw observation dumps, RSSI distributions, antenna layouts) exists in the repo to set thresholds; any numbers in a proposal would need site commissioning, as the archived blueprint itself insists ([10_BLUEPRINT_RFID_WMS_ENTERPRISE.md:143-160](../../audit/archive/2026-09/10_BLUEPRINT_RFID_WMS_ENTERPRISE.md)).
- Reader capabilities (whether the chosen Chainway reader reports phase/Doppler/per-antenna RSSI or supports GPIO triggers) are not documented in the repo; the blueprint warns not to assume capabilities of other vendors' readers ([10_BLUEPRINT_RFID_WMS_ENTERPRISE.md:29](../../audit/archive/2026-09/10_BLUEPRINT_RFID_WMS_ENTERPRISE.md)).
