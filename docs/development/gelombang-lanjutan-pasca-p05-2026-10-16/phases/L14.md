## LN-140 — Rantai bisnis dan Finance pada satu kandidat rilis

Jalankan seluruh scenario acceptance yang required pada kandidat final atau buktikan ancestry dan retest area terdampak. Utamakan chain besar: multi-entitas SO → internal purchase → receipt → MDQ → RFID → putaway → QC → multi-gudang transit → customer; Special Order → proofing berulang → produksi; samples/ecer; retur → Jakarta → QC → replacement atau credit → CST → supplier; opname; export/rapor; attendance. Simulasikan kegagalan/retry/concurrency pada batas yang mengubah saldo.

Pending terkait: Tidak ada keputusan bisnis yang ditandai pending.

Bukti kelulusan:

- **LN-140-T01** — Diberikan fixture L00, ketika semua rantai dijalankan pada kandidat, maka qty per unit, identitas, owner, alamat, reservation, dokumen, saldo customer, AR/AP, inventory valuation dan GL sesuai checkpoint dan tidak double posting.
- **LN-140-T02** — Diberikan kegagalan setelah cetak/issue/QC/settlement tetapi sebelum ACK, ketika dipulihkan, maka operasi dapat direkonsiliasi tanpa transaksi hilang atau berlipat.
## LN-141 — Migrasi dan batas cakupan yang terukur

Uji migrasi existing SO/retur/inspection/grade/permission/device job/source links tanpa merusak histori atau mengisi provenance dengan tebakan. Catat coverage requirement, acceptance dan source map, termasuk cabang pending. Plan ini melingkupi diskusi pasca-P05 dan sisa fase lama; audit wave 1–3 tetap ledger tersendiri. Tidak menyebut 100 persen semua kode/semua bug telah diperiksa dari kelulusan plan ini.

Pending terkait: Tidak ada keputusan bisnis yang ditandai pending.

Bukti kelulusan:

- **LN-141-T01** — Diberikan data lama tanpa roll link/provenance, ketika migrasi dry-run, maka ditandai membutuhkan rekonsiliasi, bukan dipasangkan ke PO produk terakhir secara otomatis.
- **LN-141-T02** — Diberikan schema baru di-rollback/dipulihkan dari backup uji, ketika dibandingkan, maka saldo dan hubungan dokumen dapat direkonsiliasi; penomoran dan posting tidak berulang.
- **LN-141-T03** — Diberikan requirement dan acceptance pending, ketika laporan cakupan dibuat, maka pending/fail/not_run dilaporkan eksplisit dan tidak masuk persentase PASS.
## LN-142 — UAT dan definisi selesai

Tutup gelombang hanya setelah seluruh requirement required validated, seluruh acceptance pass dengan bukti yang dapat dibuka, semua keputusan blocker resolved, perangkat asli diuji, migrasi/recovery lulus, tidak ada blocker operasional/finansial, dan owner menyetujui kandidat final. Penyempitan lingkup hanya melalui keputusan owner tertulis; hasilnya bernama penutupan lingkup revisi, bukan seluruh scope asli selesai. Penyusunan dokumen atau hasil simulator bukan validasi aplikasi.

Pending terkait: UAT-01

Bukti kelulusan:

- **LN-142-T01** — Diberikan requirement blocked atau acceptance not_run, ketika agent meminta complete, maka validator menolak meskipun build dan unit test lulus.
- **LN-142-T02** — Diberikan semua bukti final beserta persetujuan owner dan reviewer yang berbeda dari implementer, ketika closure dijalankan, maka SHA, tanggal, jumlah requirement/acceptance dan sisa risiko tercantum serta dapat dilacak.

## Prompt pelaksanaan fase

Kerjakan requirement fase L14 di atas. Baca AGENT_GUIDE, keputusan aktif dan sumber terkait pada COVERAGE. Periksa code, UI dan flow existing terlebih dahulu. Catat kemampuan yang cukup konfigurasi/reuse dan perubahan yang benar-benar perlu. Jangan mengubah rule yang belum diputuskan. Seluruh aktivitas baru wajib terdaftar pada custom role dan data scope. Gunakan kontrak roll/UOM/owner dan financial event dari L00.

Untuk tiap requirement, jelaskan sebelum/sesudah, API/schema/migrasi terdampak, sumber data dan efek lintas modul. Jalankan acceptance dengan input serta hasil aktual, bukan mengganti skenario menjadi test yang hanya mencerminkan implementasi. Sertakan error path, retry dan concurrency yang memengaruhi saldo/approval. Jalankan pemeriksaan repo yang diwajibkan sesuai perubahan.

Pending fase: UAT-01. Pending hanya memblok cabang terkait. Catat blocker beserta requirement terdampak, lanjutkan pekerjaan independen.

## Titik selesai fase

- Semua requirement fase berstatus validated dan acceptance di atas pass dengan hasil aktual, reviewer dan file evidence.
- Seluruh dependency tervalidasi; semua pending yang memengaruhi requirement fase resolved dengan jawaban dan sumber persetujuan.
- Phase report menjelaskan navigasi aktual, input/proses/output, dampak modul, migrasi, pengujian, risiko dan commit implementasi/verifikasi.
- Reviewer terpisah dan owner menyetujui lingkup fase; owner approval ref disimpan. Sebelum review, status maksimal implemented_pending_validation.
- Validator paket lulus; bukti fisik perangkat wajib untuk skenario hardware. Build/simulator/dokumen saja tidak memenuhi skenario perangkat nyata.

Simpan bukti di `evidence/L14/`. Update status SSOT di BACKLOG.json, lalu render dokumen turunan. Bila belum memenuhi salah satu syarat, jangan klaim fase selesai; laporkan bagian completed implementation dan blocker secara terpisah.

## LN-143 — Validasi produksi Pesanan Khusus hingga penerimaan, Finance dan pengiriman

Buktikan kedua jalur LN-033 sampai receipt actual, kualitas, alokasi SO, dispatch/customer dan rekonsiliasi Finance. Termasuk multi-item, partial, callback, source provenance, material, lifecycle guards dan regresi. Kelulusan L03 tidak menggantikan UAT rangkaian L14. Spesifikasi wajib: IMPLEMENTASI_PRODUKSI_SUPPLIER_MAKLOON.md

Bukti kelulusan:

- **LN-143-T01** — E2E supplier: ACC uji relevan -> PR/PO -> receipt parsial/final -> status kualitas yang berlaku -> stok eligible -> alokasi SO -> picking/dispatch/SJ -> customer. Qty tersisa dan status per item benar; baru PO dibuat bukan bukti produksi fisik atau barang siap kirim.
- **LN-143-T02** — E2E makloon: ACC -> PR/MKO -> reserve bahan -> issue -> receipt actual -> status kualitas yang berlaku -> alokasi SO -> pengiriman customer. Selisih output terhadap forecast tetap fakta fisik; keputusan kekurangan/amandemen mengikuti flow existing, tanpa auto-fabrikasi stok.
- **LN-143-T03** — Receipt parsial campuran supplier dan makloon pada satu Pesanan Khusus tidak membuat seluruh pesanan ready; panel tracking/pengiriman bekerja tanpa linked_po_id untuk jalur makloon dan menampilkan semua dokumen yang relevan.
- **LN-143-T04** — Dua Pesanan Khusus untuk SKU dan entitas sama menerima hasil berbeda: receipt/QC ditautkan dengan dokumen dan line asal, tidak find_one product_id yang kebetulan cocok. Penerimaan unrelated tidak mengubah status pesanan ini.
- **LN-143-T05** — Receipt dan QC callback diulang atau datang tidak berurutan: stok, alokasi, outbound task dan status tidak ganda. Barang karantina/reject atau teralokasi ke pesanan lain tidak tersedia untuk dikirim.
- **LN-143-T06** — Rekonsiliasi Finance: pembelian output supplier berbeda dari bahan milik sendiri + jasa makloon. Tidak menggandakan inventory/HPP/AP/AR; biaya pengadaan tidak menimpa harga jual Grade A atau Special Price yang disetujui. Bukti mencatat event posting actual dan invariant sebelum/sesudah.
- **LN-143-T07** — Regression SO normal, R&D internal tanpa pesanan, PR manual supplier/makloon, revalidation SKU existing, serta WMS lintas lokasi/entitas tetap berfungsi. Mutasi role/owner/location tidak menjadi jalan pintas pemenuhan.
- **LN-143-T08** — UAT dua jalur pada kandidat final menyertakan navigasi aktual, request/respons, nomor dokumen dan line, qty bahan/output/allocated/shipped, status kualitas, biaya/ledger dan evidence UI. Simulasi plan atau unit test tunggal tidak memenuhi kelulusan rangkaian ini.
