## Sasaran, dependensi dan navigasi

Tetapkan commit kerja, status P00–P10 yang sebenarnya, keputusan berlaku, dan peta dampak sebelum mengubah perilaku bisnis.

Prasyarat validasi penuh: Tidak ada fase prasyarat.. Bagian independen dapat dipersiapkan sebelum semua prasyarat tervalidasi; catat kesiapan dan jangan menutup fase lebih awal.

Navigasi target: Dokumentasi development, tracker lama, konfigurasi dan data uji; belum mengubah menu operasional.

Flow: Snapshot lama → cek HEAD main aktual → bandingkan perubahan → rekonsiliasi tracker → kontrak data/peristiwa → daftar fixture dan migrasi.

Navigasi di atas adalah rancangan konteks tugas. Cocokkan nama menu/route pada HEAD aktual; jangan mengaku menu target sudah tersedia. Saat menyerahkan hasil, berikan navigasi aktual dan langkah input → proses → output yang diuji.

## LN-001 — Baseline aktual dan rekonsiliasi fase lama

Catat full SHA target, status kerja lokal, delta terhadap snapshot, hasil pemeriksaan P01–P05 dan sisa P06–P10. Baca AGENTS repo target. Bukti lama tidak menjadi PASS otomatis pada SHA baru. Catat empat open issue P05: retur bahan parsial/loss, akses mobile retur material, race revalidation, dan label ACC spesifikasi. Perbaiki hanya setelah reproduksi/dampaknya dicatat; jangan hilangkan status belum tervalidasi.

Pending terkait: Tidak ada keputusan bisnis yang ditandai pending.

Bukti kelulusan:

- **LN-001-T01** — Diberikan repo target, ketika preflight dijalankan, maka SHA/branch/delta dan lingkungan uji tercatat, tanpa mereset pekerjaan lain.
- **LN-001-T02** — Diberikan status P05 implemented_pending_validation dan P06–P10 not_started, ketika tracker dipetakan, maka tidak ada klaim semuanya sudah tervalidasi; setiap ACC lama mempunyai disposisi dipertahankan, diuji ulang, diganti, atau pending dengan alasan.
## LN-002 — Kontrak perubahan dan keputusan belum final

Tetapkan kontrak roll, qty, owner, posisi fisik, dokumen sumber, approval, accounting event dan idempotency bersama modul terkait. Pisahkan keputusan owner, usulan desain teknis, data client, dan hasil pengujian. Simpan keputusan baru dengan tanggal serta penggantian keputusan lama.

Pending terkait: Tidak ada keputusan bisnis yang ditandai pending.

Bukti kelulusan:

- **LN-002-T01** — Diberikan keputusan yang bertentangan, ketika kontrak aktif dibuat, maka keputusan owner terbaru menang dan catatan historis tetap terbaca.
- **LN-002-T02** — Diberikan KLR-01 atau KLX-02 belum dijawab, ketika agent mengerjakan bagian independen, maka tidak ada formula cutloss atau rumus grade baru yang diaktifkan; kebutuhan dependennya tercatat blocked_by_decision.
## LN-003 — Fixture, risiko migrasi, dan rencana bukti

Siapkan fixture sintetis Kanda/Sukacita/CST, Rancamalang/Jakarta/Tasik/Tamim, shared warehouse, lebih dari satu kategori, user custom role, SO/PO/roll lintas entitas, sebagian dibayar dan belum dibayar. Inventaris migrasi existing record, rollback, backup serta rekonsiliasi stok dan ledger. Belum perlu seluruh jawaban client untuk menutup fase baseline.

Pending terkait: Tidak ada keputusan bisnis yang ditandai pending.

Bukti kelulusan:

- **LN-003-T01** — Diberikan fixture, ketika baseline dihitung, maka stok per owner/lokasi/satuan, komitmen, AR/AP dan identitas roll memiliki angka pembanding yang tersimpan.
- **LN-003-T02** — Diberikan rencana migrasi, ketika dry-run pada salinan data dilakukan, maka record yatim, duplikat dan saldo tidak seimbang dilaporkan; data produksi tidak diubah.

## Prompt pelaksanaan fase

Kerjakan requirement fase L00 di atas. Baca AGENT_GUIDE, keputusan aktif dan sumber terkait pada COVERAGE. Periksa code, UI dan flow existing terlebih dahulu. Catat kemampuan yang cukup konfigurasi/reuse dan perubahan yang benar-benar perlu. Jangan mengubah rule yang belum diputuskan. Seluruh aktivitas baru wajib terdaftar pada custom role dan data scope. Gunakan kontrak roll/UOM/owner dan financial event dari L00.

Untuk tiap requirement, jelaskan sebelum/sesudah, API/schema/migrasi terdampak, sumber data dan efek lintas modul. Jalankan acceptance dengan input serta hasil aktual, bukan mengganti skenario menjadi test yang hanya mencerminkan implementasi. Sertakan error path, retry dan concurrency yang memengaruhi saldo/approval. Jalankan pemeriksaan repo yang diwajibkan sesuai perubahan.

Pending fase: Tidak ada yang tercatat pada saat paket dibuat; temuan keputusan baru harus dicatat, bukan diasumsikan.. Pending hanya memblok cabang terkait. Catat blocker beserta requirement terdampak, lanjutkan pekerjaan independen.

## Titik selesai fase

- Semua requirement fase berstatus validated dan acceptance di atas pass dengan hasil aktual, reviewer dan file evidence.
- Seluruh dependency tervalidasi; semua pending yang memengaruhi requirement fase resolved dengan jawaban dan sumber persetujuan.
- Phase report menjelaskan navigasi aktual, input/proses/output, dampak modul, migrasi, pengujian, risiko dan commit implementasi/verifikasi.
- Reviewer terpisah dan owner menyetujui lingkup fase; owner approval ref disimpan. Sebelum review, status maksimal implemented_pending_validation.
- Validator paket lulus; bukti fisik perangkat wajib untuk skenario hardware. Build/simulator/dokumen saja tidak memenuhi skenario perangkat nyata.

Simpan bukti di `evidence/L00/`. Update status SSOT di BACKLOG.json, lalu render dokumen turunan. Bila belum memenuhi salah satu syarat, jangan klaim fase selesai; laporkan bagian completed implementation dan blocker secara terpisah.
